# Спека перед большой задачей

Спека — договор с владельцем о том, что задача должна делать, записанный в репе до кода. Формат и папки — как у [OpenSpec](https://github.com/Fission-AI/OpenSpec), но саму утилиту `openspec` не ставим: файлы пишет и переносит агент руками (почему — README playbook, «Облако и компьютер»). Сверено с документацией OpenSpec 1.16.1 (`docs/` репы OpenSpec на коммите `0fa4a97`, 07.11.2026, и страница openspec.dev/docs/getting-started) 09.11.2026. Шаблоны файлов — `templates/openspec/` в репе playbook (в клоне playbook, раздел README «Клон playbook», или на GitHub).

## Когда нужна

- Задача больше одного PR.
- Новая бизнес-логика: новое правило, расчёт или поведение, которое видит человек или другой сервис.
- Роадмап (`docs/roadmap.md`) или задача в трекере просит спецификацию.

Мелкие правки, баги, рефакторинг, документы и инфраструктура — без спеки. Сомневаешься — спроси владельца одним вопросом с рекомендуемым ответом.

## Как устроена

```
openspec/
├── specs/<область>/spec.md            # как система работает сейчас, правится только при архиве
└── changes/
    ├── <имя изменения>/
    │   ├── proposal.md                # зачем, что входит и что нет
    │   ├── design.md                  # как делаем, если нужно
    │   ├── tasks.md                   # шаги, по PR
    │   └── specs/<область>/spec.md    # дельта: что меняется в specs/<область>/spec.md
    └── archive/ГГГГ-ММ-ДД-<имя изменения>/
```

- Имя изменения — имя ветки PR со спекой (`prepare-pr.md`, шаг 1). OpenSpec требует строчные латинские буквы, цифры и одиночные дефисы; формат веток в это укладывается, если тема латиницей в нижнем регистре.
- Область — часть системы по смыслу, а не по коду: например, `auth`, `payments`, `notifications`, тоже строчными через дефис. Одно изменение может трогать несколько областей — по дельте на каждую.
- Текст пиши по-русски. Служебные слова оставь как в OpenSpec: заголовки `## ADDED Requirements`, `### Requirement:`, `#### Scenario:`, шаги `**GIVEN**`, `**WHEN**`, `**THEN**`, `**AND**` и `SHALL` или `MUST` в тексте требования. По ним утилита разбирает файлы, если её когда-нибудь поставят.

## Шаги

1. Возьми шаблоны из `templates/openspec/changes/example/` и заведи `openspec/changes/<имя изменения>/` в репе проекта.
2. `proposal.md`: зачем (какая проблема и почему сейчас), что входит, что не входит, какие области новые и какие меняются, что затронет (код, API, данные, документы).
3. Дельта `specs/<область>/spec.md` на каждую область:
   - `## ADDED Requirements` — новое поведение, `## MODIFIED Requirements` — изменённое (требование целиком, с тем же заголовком, что в `openspec/specs/`; в скобках — что было), `## REMOVED Requirements` — убранное (заголовок и почему), `## RENAMED Requirements` — переименованное (строки `- FROM: \`### Requirement: …\`` и `- TO: \`### Requirement: …\``). Лишние разделы удали.
   - `## Purpose` — только для новой области: одна-две фразы, зачем она.
   - Требование — одно наблюдаемое поведение, которое можно проверить, не видя код, с одним `SHALL` или `MUST`. Как сделано (таблицы, библиотеки, функции) — не сюда, а в `design.md`.
   - У каждого требования хотя бы один сценарий `#### Scenario: <какой случай>` с шагами GIVEN, WHEN, THEN. Кроме обычного пути — пустой ввод, ошибка, повтор, граница: сценарий для случая, поломка которого расстроила бы владельца больше всего.
4. `tasks.md`: группы шагов `## 1. …` с пунктами `- [ ] 1.1 …`; одна группа — один будущий PR. `design.md` — только если есть выбор подхода, риски или решения, которые надо объяснить; решения, которые останутся после задачи, — ещё и в `docs/decisions.md`.
5. Спека — отдельный PR только с ней, по `prepare-pr.md`; в описании — ссылка на `proposal.md`. Код до мёрджа спеки не пиши. Мёрдж владельцем — это и есть его «да» на план целиком (`rules.md`, «Общение»), отдельного подтверждения в треде не нужно.
6. PR с кодом — по `prepare-pr.md`, каждый по своей группе `tasks.md`. Сценарии из дельты становятся тестами: имя или комментарий теста называет сценарий. В описании PR — ссылка на папку изменения и какие сценарии покрыты. В том же PR отметь сделанные пункты `tasks.md` (`- [x]`).
7. Понадобилось изменить уже смёрдженную спеку — правка в той же папке изменения, в PR с кодом или отдельным; в описании PR — что поменялось в требованиях и почему. Это новое в плане, поэтому — только после «да» владельца на это конкретное изменение.
8. Последний PR задачи переносит изменение в архив, как это делает `openspec archive`:
   - Для каждой дельты обнови `openspec/specs/<область>/spec.md`. Новая область — создай файл по шаблону `templates/openspec/specs/example/spec.md`: заголовок `# <область> Specification`, `## Purpose` из дельты, `## Requirements` и требования из ADDED. Существующая — требования из ADDED допиши в конец `## Requirements`, MODIFIED замени целиком блок с тем же заголовком `### Requirement:`, REMOVED удали, у RENAMED поменяй заголовок. Остальной текст файла не трогай.
   - Убрали последнее требование области — удалять файл области можно только с «да» владельца (`rules.md`, «Только с согласия владельца»).
   - Все пункты `tasks.md` отмечены `[x]`; что решили не делать — убери из `tasks.md` и скажи в описании PR.
   - Перенеси папку в `openspec/changes/archive/ГГГГ-ММ-ДД-<имя изменения>/` (дата — день этого PR) через `git mv`, ничего в ней не меняя.
   - Задача закончилась раньше, чем планировали (владелец решил остановиться), — тот же перенос в архив, а в `openspec/specs/` — только то, что сделано.

## Чего не делаем

- Не ставим утилиту `openspec`, npm-пакет и её команды и не заводим их в CI, пока владелец не решит иначе (README playbook, «Облако и компьютер»).
- Не пишем спеку на всю систему заранее: `openspec/specs/` растёт только из архива, по области, которую задача тронула.
