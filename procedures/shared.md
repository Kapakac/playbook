# Разборы для участников (ветка `shared`)

Ветка `shared` в репе проекта — важные разборы и исследования, которыми владелец и участники обмениваются друг с другом. Участники видят репу и Telegram-группу, но не видят проекты агента, его треды и файлы проекта, поэтому то, что им нужно прочитать, лежит здесь. Это не план проекта: план, стек и решения — в `docs/` в `main`.

Ветка отдельная от `main` (без общей истории с ним) и никуда не мёрджится: разбор попадает в неё коммитом агента автора, без PR и без мёрджа владельцем, поэтому никто никого не ждёт. Имя ветки одно для всех проектов: по нему общий бот раз в сутки сообщает в тему проекта в группе о новых коммитах в ней. В корне ветки — `README.md`, `.github/workflows/secrets.yml` (поиск секретов) и разборы `ГГГГ-ММ-ДД-тема.md`. Как завести ветку в проекте — README playbook, раздел «Ветка shared».

Когда: владелец или участник просит сохранить разбор для коллег (например: «Оформи этот разбор для коллег в ветке `shared` по `docs/playbook/shared.md`. Тема: …»), или «кря» без подробностей не понять (`send-to-group.md`, шаг 4).

1. Проверь, можно ли это показывать другим людям: секреты (токены, пароли, ключи, содержимое `.env`) и всё, что по разделу проекта нельзя показывать (например, то, что идёт только владельцу в личку), в ветку не кладут. Эта проверка — только на тебе: поиск секретов из шага 7 ловит лишь ключи и токены, а данные, запрещённые правилами проекта, не заметит. Сомневаешься — спроси владельца. Репа проекта может быть публичной: тогда разбор видят все.
2. Если разбор не попросили прямо, предложи тему и короткое содержание тому, для кого работаешь (владельцу или участнику), и жди его «да». Просьба участника о разборе — достаточное согласие на коммит в `shared`.
3. Один разбор — один файл `ГГГГ-ММ-ДД-тема.md` в корне ветки, тема латиницей через дефис, например `2026-10-21-llm-budget.md`. Дата — день, когда пишешь.
4. Пиши по-русски, просто и так, чтобы было понятно без треда: что случилось или что предлагается, что проверено, а что нет, что нужно от читателя. Ссылки — только на GitHub: файлы проекта и треды агента участники не откроют.
5. Возьми ветку с GitHub, не трогая текущую ветку задачи, например отдельной папкой: `git fetch origin shared && git worktree add <временная папка> origin/shared`. Если ветки `shared` на GitHub нет, скажи владельцу, что проект её ещё не завёл (README playbook, раздел «Ветка shared»), и сам не заводи.
6. Положи файл, закоммить только его (автор — из раздела проекта, у участника — его собственный аккаунт) и запушь: `git push origin HEAD:shared`. Без PR. Если пуш отклонён, потому что в ветке появились чужие коммиты, сделай `git pull --rebase origin shared` и запушь снова, `--force` не используй. Временную папку потом убери (`git worktree remove`).
7. Дождись workflow `secrets` на своём коммите (вкладка Actions репы проекта или GitHub-инструменты агента).
   - Зелёный — дальше.
   - Красный — сканер нашёл похожее на секрет; в логе секрет скрыт, там файл и строка. Убери секрет из файла новым коммитом в `shared` и сразу скажи владельцу: секрет надо отозвать (выпустить новый ключ, старый отключить), потому что из истории ветки он сам не исчезнет и его уже могли увидеть. Ложное срабатывание — тоже скажи владельцу, сам сканер не отключай.
8. Ссылка для читателей: `https://github.com/<репа>/blob/shared/<файл>`. Дай её тому, для кого работаешь; в группу она уходит только через «кря» с «да» владельца (`send-to-group.md`), о самом коммите бот сообщит в группу сам.

Поправить разбор — новый коммит в `shared` по шагам 1 и 5–7. Удалить файл из ветки — только с «да» владельца, как любое удаление по общим правилам. Историю ветки не переписывать.
