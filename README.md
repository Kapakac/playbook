# Playbook

Общие правила для всех проектов владельца, одинаковые для любого агента (Claude Code, Codex, Cursor, Copilot и других). Своих правил у проектов остаётся только то, что касается их самих.

## Что здесь

- `rules.md` — общие правила.
- `procedures/` — процедуры по шагам: подготовить PR, «кря» в Telegram, ящик `/quack`, разборы для участников в ветке `shared`, новый тред, журнал сессий и доска трекера задач (обе необязательные), блок правил для агента без репы.
- `templates/` — стартовые файлы проекта.
- `init.sh` — завести новый проект из шаблонов.
- `scripts/sync-rules.sh` — синхронизация и проверка правил в репе проекта.
- `scripts/update-rules.sh` — то же для автообновления: синхронизирует, только если в playbook есть что-то новое, и дописывает новые строки шаблона PR.
- `scripts/ci-changes.sh` — для CI проектов: поменялись ли в PR только документы (раздел «CI не гоняем на документах»).
- `scripts/check-pr.sh` — для CI проектов: имя ветки, заголовок PR, автор коммитов, следы агента, строка «Список playbook сверен» и заполненная строка «README:» в описании PR по общим правилам (его запускает `rules.yml`).
- `scripts/check-rules-size.sh` — потолок длины `rules.md` (`make lint`).
- `scripts/notify-rules.sh` и workflow `.github/workflows/rules-notify.yml` — после мёрджа правил в `main` playbook запускают рассылку новых правил по проектам (раздел «Автообновление правил», «Запуск сразу после мёрджа»).
- `AGENTS.md` — правила для агента, который правит саму playbook; `CLAUDE.md` подключает его для Claude.

## Как это устроено в репе проекта

- `AGENTS.md` — инструкции для всех агентов. Сверху название и пара строк о проекте, затем между метками `<!-- playbook:begin … -->` и `<!-- playbook:end -->` копия `rules.md` (в метке записан коммит playbook, из которого она взята), а под блоком раздел «Проект»: устройство, команды, параметры для общих правил и правила самого проекта.
- Необязательные процедуры включаются строкой в разделе «Проект». Сейчас их две: журнал сессий — «Журнал сессий: ведём, ветка `<имя>`» — и доска трекера задач — «Трекер: ведём» (`procedures/tracker.md`). Строки нет — журнал не пишут и доску не ведут.
- `CLAUDE.md` — одна строка `@AGENTS.md`. Новые версии Claude Code читают `AGENTS.md` и сами, но только когда `CLAUDE.md` нет; импорт работает во всех версиях и в облачных тредах, а дважды файл не загрузится ([документация](https://code.claude.com/docs/en/memory#agents-md)).
- `docs/playbook/` — копия `procedures/`.
- Ветка `shared` — разборы для других участников (`procedures/shared.md`), отдельная от `main`. В её корне `README.md` и workflow поиска секретов из `templates/shared/`: раздел «Ветка shared».
- `make sync-rules` — обновить блок и `docs/playbook/` из клона playbook рядом с проектом (по умолчанию `../playbook`).
- `make check-rules` и workflow `.github/workflows/rules.yml` — CI падает, если блок или процедуры поправили руками, и предупреждает (не падает), если в playbook появились правила новее. На PR тот же workflow запускает `scripts/check-pr.sh` из `main` playbook: имя ветки `<ключ>-…`, заголовок PR с ключом, автор каждого коммита — человек, а не агент, и никаких следов агента в сообщениях коммитов и тексте PR (`rules.md`, «Ветки, коммиты и PR»). Ветка `claude/…`, навязанная средой, даёт только предупреждение. Ещё он краснит PR, если строки «Список playbook сверен» нет или после её коммита в playbook поменялись раздел «Что должно быть в проекте», `templates/` или `procedures/no-repo-agent.md` (`procedures/checklist.md`); Ещё — если в описании PR нет заполненной строки шаблона «README: обновлён / не нужно, потому что …»: годится «README: обновлён» (можно с подробностями) или «README: не нужно, потому что <причина>», а строка как в шаблоне или «не нужно» без причины — нет (`procedures/prepare-pr.md`, шаг 10). PR автообновления правил (ветки `*-rules-auto`) и PR самой playbook (у неё нет шаблона PR) эти две проверки пропускают. Проверка запускается и при правке заголовка или описания PR (`edited`): среда дописывает подпись при создании PR, агент её убирает, и проверка видит уже чистый текст.
- `.claude/settings.json` и `.claude/hooks/check-commit.sh` — для Claude Code на компьютере: запрет `ssh`, `scp`, `sftp`, `rsync`, `rm -rf`, force-push и push в `main`, а хук не даёт сделать коммит со служебными строками. Облачный тред и другие агенты эти файлы не читают, поэтому это дополнение к рулсету и CI, а не замена.
- Workflow `.github/workflows/rules-update.yml` — автообновление правил: раздел «Автообновление правил».
- В CI проекта (`.github/workflows/ci.yml`) первая job `changes` смотрит, что поменялось, и тяжёлые проверки не запускаются, если поменялись только документы: раздел «CI не гоняем на документах».

Почему копия, а не ссылка на playbook: Codex и часть других агентов не умеют подключать файл из `AGENTS.md` ссылкой, им нужен текст в самом файле.

## Новый проект

Проект заводит агент в собственном проекте новой репы, первым PR.

### Что делает владелец

1. Создаёт репу для проекта на GitHub с README (галочка «Add a README file»): в совсем пустой репе нет ветки `main`, и PR открыть некуда.
2. Подключает к проекту (в Claude — в настройках проекта, раздел с репозиториями) новую репу и репу playbook.
3. Пишет агенту в этом проекте:

   > Заведи проект по playbook: README playbook, раздел «Новый проект», часть «Что делает агент». Проект: <пара строк, что это и зачем>.

4. Проверяет PR агента и мёрджит его.
5. Пишет короткую инструкцию проекта (в Claude — в настройках проекта): агент предложит текст в PR.
6. Включает в репе настройку для автообновления правил (раздел «Автообновление правил»). Если настроен запуск сразу после мёрджа, добавляет новую репу в список рассылки и в её токен (там же, «Запуск сразу после мёрджа»).
7. Защищает `main` (раздел «Защита main»): если в справочнике группы есть workflow, который ставит защиту всем репам группы, добавляет репу в его список и в его токен; иначе ставит рулсет руками. Приватной репе на бесплатном плане GitHub рулсет недоступен — шаг пропускается.

### Что делает агент

1. Находит клон playbook рядом с репой проекта (`../playbook`). Если его нет, клонирует его туда сам или просит владельца подключить репу к проекту. Обновляет клон до свежего `main` (раздел «Клон playbook»).
2. Спрашивает у владельца то, чего нет в его сообщении и что нельзя придумать: ключ проекта, автор коммитов, нужен ли бот и ящик `/quack`, вести ли журнал, нужны ли разборы для участников (ветка `shared`), есть ли справочник группы. Вопросы — по одному за сообщение, у каждого рекомендуемый ответ и одна фраза, зачем он нужен (`rules.md`, «Общение»). Собрав ответы, показывает план целиком и ждёт одного подтверждения.
3. Создаёт ветку по общим правилам и запускает `../playbook/init.sh . "<Название проекта>"`. Скрипт копирует шаблоны, не трогая существующие файлы, и сразу вклеивает общие правила (`make sync-rules`).
4. Заполняет раздел «Проект» в `AGENTS.md`, `docs/stack.md` и `docs/roadmap.md` по ответам и описанию владельца, а в `README.md` — раздел «Что умеет и как пользоваться» (пока проект ничего не умеет — одной строкой, что он будет делать).
5. Заводит ветку `shared` по разделу «Ветка shared», часть «Что делает агент», шаг 3 (`init.sh` её не создаёт). Если разборы для участников проекту не нужны, ветку не заводит, а пишет в раздел «Проект» строку «Ветку shared не ведём: <причина>.» (раздел «Ветка shared», часть «Если ветка не нужна»).
6. Открывает PR по `docs/playbook/prepare-pr.md`. В описании PR — готовый короткий текст инструкции проекта для владельца: строки проекта и под ними блок из `docs/playbook/no-repo-agent.md` без правок (координатор проекта репу не видит и знает правила только из инструкции).

## Перевести существующий проект

Перевод делает агент в собственном проекте той репы, одним PR. Каждый проект переводится отдельно.

### Что делает владелец

1. Подключает репу playbook к этому проекту (в Claude — в настройках проекта, раздел с репозиториями), чтобы агент видел её рядом с репой проекта.
2. Пишет агенту в этом проекте:

   > Переведи проект на общие правила из playbook: README playbook, раздел «Перевести существующий проект», часть «Что делает агент».

3. Проверяет PR агента и мёрджит его.
4. После мёрджа заменяет инструкцию проекта (в Claude — в настройках проекта) коротким текстом, который агент предложил в PR.
5. Включает в репе настройку для автообновления правил (раздел «Автообновление правил»).

### Что делает агент

1. Находит клон playbook рядом с репой проекта (`../playbook`). Если его нет, клонирует его туда сам или просит владельца подключить репу к проекту. Обновляет клон до свежего `main` (раздел «Клон playbook»).
2. Создаёт ветку по общим правилам и `AGENTS.md` из `templates/AGENTS.md`.
3. Переносит в раздел «Проект» всё своё, что относится только к этому проекту: из старого `CLAUDE.md` и из инструкции проекта (у кого `CLAUDE.md` нет — только из инструкции). Общие правила, которые уже есть в `rules.md`, не переносит. Чего нет в старых правилах и нельзя придумать, спрашивает у владельца по одному вопросу за сообщение, с рекомендуемым ответом (`rules.md`, «Общение»). Заполняет параметры: ключ проекта, автор коммитов, бот, ящик `/quack`, адресат «кря», хелпер тестов, внешние сервисы, справочник группы. Если проект ведёт журнал, добавляет строку «Журнал сессий: ведём, ветка …» с нынешней веткой журнала. Подраздел «Агент может без вопроса» — как в шаблоне, пустой: пункты в него добавляет владелец.
4. Заменяет `CLAUDE.md` одной строкой `@AGENTS.md`.
5. Добавляет в `Makefile` цели `sync-rules` и `check-rules` из `templates/Makefile`, в `.github/workflows/` — `templates/.github/workflows/rules.yml` и `rules-update.yml`, в `.claude/` — `settings.json` и `hooks/` из `templates/.claude/` (если `settings.json` уже есть, дописывает в него `deny` и хук из шаблона, своё оставляет), а если нет шаблона PR — `templates/.github/pull_request_template.md`. В CI проекта добавляет job `changes` по разделу «CI не гоняем на документах» (если CI нет — берёт `templates/.github/workflows/ci.yml`).
6. Запускает `make sync-rules`, затем `make check-rules`.
7. Если есть скиллы `.claude/skills/prepare-pr` и `send-to-group`, сводит их к ссылке на `docs/playbook/`.
8. Заводит ветку `shared` по разделу «Ветка shared», часть «Что делает агент», шаги 2–4. Если в разделе «Проект» есть строка «Ветку shared не ведём: …», шаг пропускает.
9. Если в `docs/duck-log.md` нет строки «Просмотрено до №N», добавляет её с самым большим уже разобранным номером. Если у проекта ящик есть, а `docs/duck-log.md` нет, берёт его из `templates/docs/`.
10. Открывает PR по `docs/playbook/prepare-pr.md`. В описании PR — что из старых правил куда переехало, какие правила проекта расходились с общими и чем их заменили, и готовый короткий текст новой инструкции проекта для владельца: строки проекта и под ними блок из `docs/playbook/no-repo-agent.md` без правок.

## Что должно быть в проекте

Один список всего, что проекту нужно от playbook. Часть правок playbook требует потом что-то сделать в каждом проекте руками; чтобы не вспоминать каждую по отдельности, проект сверяют с этим списком. Агент проекта сам замечает, что список поменялся с прошлой сверки, и в начале треда предлагает доделать недостающее (`procedures/checklist.md`): общий блок `AGENTS.md` обновляется автоматически, а пункты вне него — только так.

Новый пункт добавляется в список в том же PR playbook, который требует от проектов ручного шага.

### Что делает владелец

Обычно ничего: агент проекта сам предлагает сверку, когда список поменялся, и владелец отвечает «да». Сверить без повода (например, впервые) — пишет агенту в проекте:

> Сверь проект со списком из playbook и доделай, чего не хватает: README playbook, раздел «Что должно быть в проекте».

Затем отвечает на вопросы агента, мёрджит его PR и делает то, что агент попросил сделать руками (настройки репы, бот).

### Что делает агент

1. Обновляет клон playbook (раздел «Клон playbook») и проходит по списку.
2. Показывает владельцу итог по каждому пункту: есть, нет или не смог проверить (и почему). Пункты владельца (настройки репы, инструкция проекта, бот) — отдельно, с тем, что ему сделать.
3. Владелец уже попросил доделать, поэтому отдельного «да» не ждёт. Недостающее в `main` доделывает одним PR по `docs/playbook/prepare-pr.md`, по шагам из колонки «Где описано»; ветку `shared` — коммитом в неё по разделу «Ветка shared». Что-то удалить или перенести (например, старые разборы из `main`) — только после «да» владельца.
4. В том же PR обновляет строку «Список playbook сверен» на текущий коммит playbook (строки нет — добавляет её в «Параметры для общих правил»). В описании PR — что из списка уже было, что добавлено и что осталось владельцу.

## Начать работу в проекте

Для участника, которого владелец позвал в проект. Своих правил у участника нет: работа идёт по `rules.md` и разделу «Проект» в `AGENTS.md` репы проекта. Начинать можно с любым агентом и в любой среде: человек делает шаги из первой части, а потом пишет агенту фразу, с которой агент делает вторую.

### Что делает участник

1. Пришли владельцу свой ник на GitHub и скажи, в какой проект. Доступ к репе проекта даёт он; эта репа публичная, к ней доступ не нужен.
2. Возьми агента, который работает с кодом: читает репу, запускает команды и пушит (Claude Code, Codex, Cursor, GitHub Copilot и т.п.). Обычный чат (ChatGPT, обычный чат Claude и т.п.) не подойдёт.
3. Создай в агенте проект и подключи к нему репу проекта (в Claude — проект и его репозитории в настройках, в Codex — среда с этой репой, в Cursor — папка с клоном). Эту репу подключать не нужно: агент прочитает этот раздел с GitHub. Если он не может (в среде закрыт интернет), разреши в настройках среды доступ к GitHub (он всё равно нужен для git и PR) или подключи и эту репу (тогда вводные из шага 4 обязательны).
4. Вставь в инструкции проекта своего агента вводные (в Claude — инструкция проекта, в Codex — настройки среды, в Cursor — правила; не нашёл где — спроси агента):

   > Правила проекта — в `AGENTS.md` репы `<владелец>/<репа проекта>`: общий блок из playbook и раздел «Проект». Следуй им. Репу playbook только читаем. Я участник, а не владелец: где правила требуют согласия владельца, нужно его «да», а не моё.

   Если участник обсуждает проект и в обычном чате (ChatGPT, обычный чат Claude и т.п.), в инструкции того чата вставляется блок из `docs/playbook/no-repo-agent.md` репы проекта: такой чат `AGENTS.md` не видит.

   Вводные обязательны, если агент видит несколько реп со своим `AGENTS.md` (к проекту подключена и эта репа, или агент открыт в папке, где лежат обе) или сам не читает `AGENTS.md`: иначе он может взять правила не той репы. Можно без них, если агент открыт в папке репы проекта и читает `AGENTS.md` сам (Claude — через `CLAUDE.md`), а других реп с `AGENTS.md` не видит. Не уверен — вставь: они не мешают.
5. На компьютере склонируй рядом репу проекта и эту репу в папку `playbook`, чтобы получилось `<папка>/<репа проекта>` и `<папка>/playbook`. Правила и процедуры уже лежат в репе проекта (`AGENTS.md` и `docs/playbook/`), а клон рядом нужен `make sync-rules` и `make check-rules`. Агента открывай в папке репы проекта.
6. Напиши агенту фразу (её же даёт бот в Telegram), с `<владелец>/playbook` как в адресе этой страницы:

   > Начни работу по README репы `<владелец>/playbook`, раздел «Начать работу в проекте».

### Что делает агент

Эта часть — для агента, которого попросили начать работу по этому разделу. Он только читает и проверяет: ничего не меняет (файлы, ветки, `git config`, настройки среды), пока человек не попросит.

1. Читает раздел [«Облако и компьютер: что учесть агенту»](#облако-и-компьютер-что-учесть-агенту) (с подразделом про себя), затем `AGENTS.md` и `README.md` репы проекта. Если репы проекта не видно, говорит человеку, что её нужно подключить к проекту агента или склонировать, а если нет доступа — попросить его у владельца, и на этом останавливается.
2. Проверяет среду по пунктам того раздела:
   - читает ли он `AGENTS.md` репы проекта сам и видит ли инструкции проекта; какие ещё репы с `AGENTS.md` ему видны;
   - доступ к GitHub: работает ли `git fetch` репы проекта; право на push без настоящего пуша часто не проверить — тогда так и сказать;
   - есть ли (и запущены ли) Docker и инструменты для `make lint` и `make test` из раздела «Проект»; есть ли клон playbook рядом (`../playbook`) и видна ли репа справочника группы, если она есть в разделе «Проект»;
   - автор коммитов (`git config user.name` и `user.email`): у участника — его собственный аккаунт, не владелец и не агент.
3. Коротко рассказывает человеку:
   - что за проект (пара строк из `README.md` и `AGENTS.md`), ключ проекта и команды;
   - что нельзя без согласия владельца: общий список из `rules.md` («Только с согласия владельца»; «кря» в Telegram — «Процедуры») и правила проекта. Согласие — «да» самого владельца, а не участника;
   - как работать: ветка `<ключ проекта>-<задача>-<тема>-<суффикс>`, заголовок PR с ключа, коммиты с аккаунта участника, перед PR — `docs/playbook/prepare-pr.md`, в `main` не пушить, PR мёрджит владелец;
   - как поделиться исследованием с коллегами: написать агенту «Разбор для коллег: <тема>» — агент сам закоммитит разбор в ветку `shared`, без PR, а бот раз в сутки сообщит о нём в тему проекта в группе;
   - если у проекта есть ящик `/quack`: заметки для агента пишутся в Telegram-группе командой `/quack <метка> …` (метка — в разделе «Проект»), агент разбирает их по `docs/playbook/quack-inbox.md` и ничего по ним не делает без «да» владельца;
   - что в среде не работает или не проверено и как это исправить (что поменять в настройках среды или поставить на компьютере).
4. Если вводных из шага 4 первой части в инструкциях проекта нет (или агенту не видно, есть ли они), даёт их текст с подставленной репой проекта и говорит, нужны ли они в этой среде обязательно и куда их вставить.

## Поменять общие правила

1. Правка — PR в playbook (`rules.md`, `procedures/`, шаблоны или скрипты). Перед PR — `make lint` и `make test`.
2. После мёрджа в каждом проекте с автообновлением через несколько минут (если настроен запуск сразу после мёрджа, раздел «Автообновление правил»), иначе по расписанию рассылки или по кнопке откроется и сразу смёрджится PR «<ключ>: обновить общие правила» (раздел «Автообновление правил»). Если мёрдж не прошёл, PR остаётся открытым: владелец проверяет его и мёрджит. Если workflow не справился (ошибка, в шаблоне PR в playbook строки убрали или изменили) или автообновления в проекте нет, владелец пишет агенту проекта: «Обнови общие правила из playbook». Агент обновляет клон playbook (раздел «Клон playbook»), запускает `make sync-rules`, сверяет `.github/pull_request_template.md` проекта с `templates/.github/pull_request_template.md` и добавляет в него новые строки из playbook (свои строки проекта не трогает), затем открывает отдельный PR. Что добавил в шаблон — в описании PR.

При правке помни:

- Репа публичная: никаких секретов, имён, ников и других личных данных, названий и подробностей конкретных проектов. Всё конкретное — в разделе «Проект» самих проектов.
- `rules.md` вклеивается в `AGENTS.md` каждого проекта, а Codex читает не больше 32 КиБ инструкций на все `AGENTS.md` вместе. Поэтому `rules.md` держим коротким, подробности — в процедурах: `make lint` падает, если в нём больше 60 строк или 8 КиБ (`scripts/check-rules-size.sh`). Правило, которое можно проверить кодом или настройкой (CI, рулсет, `deny` агента), делаем проверкой, а в тексте оставляем одну фразу или ничего.
- Правило, которое касается одного проекта, сюда не кладём: ему место в разделе «Проект» того проекта.
- Если после правки проектам нужно что-то сделать руками (новый параметр в разделе проекта, новый файл), напиши это в описании PR и добавь пункт в раздел «Что должно быть в проекте»: агенты проектов заметят новый пункт сами (`procedures/checklist.md`), отдельная фраза в каждом проекте не нужна.
- `scripts/ci-changes.sh` и `scripts/check-pr.sh` CI проектов берёт прямо из `main` playbook, без PR в проекте: ошибка в них сразу ломает CI всех проектов. Если сомневаешься, `ci-changes.sh` должен отвечать «это код» (`code=true`), а `check-pr.sh` — пропускать.
- Своих `docs/` у playbook нет: агент открывает эту репу только для правки правил. `AGENTS.md` отсылает к `rules.md` и даёт параметры вместо раздела «Проект»: так агент на компьютере владельца, где нет инструкции проекта, знает правила и то, что репа публичная. `CLAUDE.md` подключает `AGENTS.md` и `rules.md` для Claude.

## Автообновление правил

Workflow `rules-update.yml` в репе проекта по кнопке и от рассылки (ниже, «Запуск сразу после мёрджа») берёт свежий `main` playbook и запускает `scripts/update-rules.sh`. Если с коммита в метке `AGENTS.md` в playbook поменялись `rules.md`, `procedures/` или шаблон PR, скрипт делает `make sync-rules`, дописывает в `.github/pull_request_template.md` проекта строки, которые появились в шаблоне playbook, и проверяет результат (`make check-rules`). Изменения уходят в PR «<ключ>: обновить общие правила» из ветки `<ключ>-rules-auto`; ключ и автор коммита берутся из раздела проекта.

- Токен не нужен: playbook публичная, а PR открывает встроенный токен GitHub Actions (`GITHUB_TOKEN`).
- Этот PR workflow мёрджит сам сразу после открытия, тем же встроенным токеном. Это единственное исключение из правила «PR мёрджит владелец»: в PR только копия общих правил, процедур и строк шаблона PR, которые владелец уже проверил и смёрджил в playbook, а `make check-rules` прошёл в самом workflow. Если мёрдж не прошёл (например, конфликт), в логе запуска будет предупреждение, а PR останется открытым: его проверяет и мёрджит владелец.
- Проверки проекта на таком PR не запускаются, и мёрдж не запускает деплой проекта: события от встроенного токена не запускают другие workflow ([документация](https://docs.github.com/en/actions/concepts/security/github_token)).
- Ветку `<ключ>-rules-auto` workflow каждый раз пересоздаёт от `main` и пушит с `--force`: свои правки в неё не коммить.
- Строки, которые в шаблоне PR playbook убрали или изменили, и строки, которые проект у себя удалил, workflow не трогает: это работа агента по «Обнови общие правила из playbook».
- Инструкции проектов в Claude и других агентах workflow не меняет.

### Запуск сразу после мёрджа

Чтобы не ждать утра и не нажимать кнопку в каждом проекте, playbook после мёрджа сама запускает рассылку: workflow `rules-notify.yml` срабатывает на пуш в `main`, если в нём поменялись `rules.md`, `procedures/` или `templates/.github/pull_request_template.md` (а ещё сам этот workflow и `scripts/notify-rules.sh`, чтобы их правку было видно сразу после мёрджа). Он вызывает по API кнопку рассылки — workflow `rules-update-all.yml` в ветке `main` отдельной приватной репы владельца, — а рассылка запускает `rules-update` во всех проектах из своего списка.

- Playbook публичная, и её логи Actions видны всем. Поэтому название репы рассылки и список проектов в playbook не пишем: репа — только в секрете `RULES_NOTIFY_REPO`, список — в самой рассылке.
- Своего расписания у `rules-update.yml` в проекте нет: раз в день его запускает рассылка по своему расписанию, на случай если запуск после мёрджа не прошёл. Так механизм один, а не два. Рассылки нет — правила доходят по кнопке `rules-update` в каждом проекте или по «Обнови общие правила из playbook».
- Секретов нет — запуск зелёный с предупреждением: проекты получат правила по расписанию рассылки или по кнопке. Вызов не прошёл (нет репы или права у токена, кончился срок) — запуск красный.
- Если одна правка запустит `rules-update` в проекте дважды (после мёрджа и по расписанию рассылки), второй запуск ничего нового не найдёт и PR не откроет. Петли нет: PR правил в проектах мёрджит встроенный токен, а его действия другие workflow не запускают.

Что делает владелец, один раз (рассылка `rules-update-all.yml` с запуском по кнопке, `workflow_dispatch`, уже должна быть):

1. Создаёт токен: [новый fine-grained токен](https://github.com/settings/personal-access-tokens/new) (аватар → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token). Token name — `playbook-rules-notify`, Expiration — на выбор (кончится срок — запуск после мёрджа станет красным, правки будут доходить по расписанию рассылки). Resource owner — свой аккаунт, Repository access → Only select repositories → только репа рассылки. Permissions → Repository permissions → Actions → Read and write, больше ничего. Generate token, скопировать.
2. В playbook: Settings → Secrets and variables → Actions → New repository secret. Name — `RULES_NOTIFY_TOKEN`, Secret — токен, Add secret. Ещё один: Name — `RULES_NOTIFY_REPO`, Secret — `<владелец>/<репа рассылки>`, Add secret.
3. Проверяет: после следующего мёрджа, который меняет правила, во вкладке Actions playbook зелёный запуск `rules-notify` без предупреждения, а в репе рассылки — запуск `rules-update-all` с событием `workflow_dispatch`.

### Что делает владелец

1. В репе проекта: Settings → Actions → General → Workflow permissions → включить «Allow GitHub Actions to create and approve pull requests» и сохранить. По умолчанию в личной репе она выключена, и без неё workflow не откроет PR ([документация](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)).
2. В проекте, который уже переведён на playbook, пишет агенту:

   > Подключи автообновление общих правил: README playbook, раздел «Автообновление правил», часть «Что делает агент».

3. После мёрджа PR агента — первый запуск по кнопке: вкладка Actions → `rules-update` → Run workflow.

### Что делает агент

1. Обновляет клон playbook (раздел «Клон playbook»).
2. Создаёт ветку по общим правилам и копирует `templates/.github/workflows/rules-update.yml` в `.github/workflows/`. Если файл уже есть, заменяет его шаблоном целиком: так в проект приезжают правки workflow, например снятое ежедневное расписание (`schedule`).
3. Проверяет, что строки «Ключ проекта» и «Автор коммитов» в разделе «Проект» написаны как в `templates/AGENTS.md`, со значением в обратных кавычках: workflow читает их оттуда.
4. Обновляет документы проекта, где перечислены workflow (`README.md`, раздел «Проект» в `AGENTS.md`).
5. Открывает PR по `docs/playbook/prepare-pr.md`. В описании PR — напоминание владельцу про настройку из шага 1 и первый запуск по кнопке.

## CI не гоняем на документах

Если в PR поменялись только документы, тяжёлые проверки CI (линтеры, тесты, сборка) не запускаются: ждать их долго, а минуты раннеров тратятся зря.

- Первая job `changes` в CI проекта берёт свежий `main` playbook и запускает `scripts/ci-changes.sh`. Он сравнивает PR с базовой веткой (при пуше в `main` — с прошлым состоянием `main`) и выдаёт `code=false`, если все изменённые файлы — документы, иначе `code=true`.
- Документы — это `*.md` в корне репы и в `.github/` (шаблон PR), всё в `docs/` и в `shared/`. `*.md` в других папках (например, фикстуры тестов) считаются кодом. Если в `docs/` лежит что-то, что читает код, — `--code '<маска>'`: такой файл всегда код.
- Если сравнить не получилось (новая ветка, история переписана), скрипт отвечает `code=true`: лучше прогнать лишний раз, чем пропустить.
- Тяжёлые job получают `needs: changes` и `if: needs.changes.outputs.code == 'true'`. Пропущенная по `if` job для обязательных проверок (branch protection) считается пройденной, поэтому PR из одних документов не повиснет в ожидании ([документация](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks#handling-skipped-but-required-checks)). Простой `paths-ignore` в `on:` для этого не годится: workflow не запустится совсем, и обязательная проверка будет ждать вечно.
- Не пропускаем: проверку общих правил (`rules.yml`, это отдельный workflow) и поиск секретов (gitleaks и т.п.): они быстрые, а секрет можно случайно вставить и в документ.
- Пример — `templates/.github/workflows/ci.yml` (новый проект получает его от `init.sh`) и CI самой playbook.
- Если деплой запускается после успешного CI в `main`, он, как и раньше, запустится и после мёржа одних документов: CI при этом зелёный.

### Что делает владелец

Пишет агенту в проекте:

> Сделай, чтобы CI не гонялся на правках документации: README playbook, раздел «CI не гоняем на документах», часть «Что делает агент».

### Что делает агент

1. Обновляет клон playbook (раздел «Клон playbook») и создаёт ветку по общим правилам.
2. Добавляет в `.github/workflows/ci.yml` проекта job `changes` из `templates/.github/workflows/ci.yml` и вешает `needs: changes` и `if: needs.changes.outputs.code == 'true'` на тяжёлые job. Job, которые уже ждут другую (`needs: [...]`), пропустятся сами, но `changes` в их `needs` не помешает. Поиск секретов не трогает.
3. Проверяет, не читает ли код или тесты файлы из `docs/`, `shared/` или `*.md` в корне. Если читает — добавляет их маски через `--code`.
4. Обновляет документы проекта, где описан CI (`README.md`, раздел «Проект» в `AGENTS.md`).
5. Открывает PR по `docs/playbook/prepare-pr.md`. Этот PR меняет код CI, поэтому проверки на нём пройдут полностью. В описании PR — какие job теперь пропускаются на документах.

## Ветка shared

Разборы для участников (`procedures/shared.md`) живут в ветке `shared` репы проекта, а не в `main`: это обмен в обе стороны, владелец ↔ участники, и никто не должен ждать мёрджа. Агент автора коммитит разбор прямо в ветку, без PR. О новых коммитах в ней раз в сутки сообщает общий бот, в тему проекта в группе, поэтому имя ветки одно для всех проектов.

- Ветка отдельная от `main`, без общей истории (`--orphan`), и никуда не мёрджится. В корне — `README.md` и `.github/workflows/secrets.yml` из `templates/shared/` и разборы `ГГГГ-ММ-ДД-тема.md`.
- `secrets.yml` при каждом пуше в `shared` ищет секреты (gitleaks) в новых коммитах и падает, если нашёл. Лежит он в самой ветке: workflow на `push` GitHub берёт из запушенного коммита, файл в `main` для этой ветки не запустится. Сканер ловит только ключи и токены; данные, которые нельзя показывать по правилам проекта, проверяет только агент автора перед коммитом.
- `init.sh` и `make sync-rules` ветку не трогают. Если в playbook поменялся шаблон из `templates/shared/`, PR playbook об этом скажет, и проекты обновляют его в ветке коммитом.
- Ссылка на разбор: `https://github.com/<репа>/blob/shared/<файл>`.

### Если ветка не нужна

Если проекту разборы для участников не нужны (например, инфраструктурному), это записано строкой в разделе «Проект» его `AGENTS.md`, в «Параметрах для общих правил»: «Ветку shared не ведём: <причина>.» Агент с такой строкой ветку `shared` не заводит и пропускает шаги и пункты про неё: в «Новом проекте», «Переводе существующего проекта» и «Что должно быть в проекте». Просьбу о разборе в таком проекте агент не выполняет, а говорит, что ветку здесь не ведём (`procedures/shared.md`, шаг 5). Понадобилась ветка — владелец просит её завести, и агент убирает строку (шаг 1 ниже).

### Что делает владелец

1. Пишет агенту в проекте:

   > Заведи ветку shared для разборов: README playbook, раздел «Ветка shared», часть «Что делает агент».

2. Если в `main` уже есть разборы (папка `shared/` или похожая), отвечает агенту, переносить ли их и убирать ли из `main`.
3. Чтобы о разборах сообщал бот, проект должен быть у бота (в проекте бота).

### Что делает агент

1. Обновляет клон playbook (раздел «Клон playbook»). Если в разделе «Проект» есть строка «Ветку shared не ведём: …», а владелец сам попросил завести ветку, убирает эту строку в PR из шага 5.
2. Проверяет, есть ли ветка на GitHub: `git ls-remote --heads origin shared`. Если есть — сверяет, что в её корне есть `README.md` и `.github/workflows/secrets.yml` как в `templates/shared/`, недостающее добавляет коммитом в неё и переходит к шагу 4.
3. Заводит ветку отдельной папкой, не трогая свою рабочую: `git worktree add --detach <временная папка>`, в ней `git switch --orphan shared`, копирует туда содержимое `../playbook/templates/shared/` (с `.github/`), коммитит эти два файла с автором из раздела проекта и пушит `git push origin shared`. Дожидается зелёного `secrets` на этом коммите, затем `git worktree remove <временная папка>`.
4. Если в `main` уже лежат разборы, ничего не переносит и не удаляет сам: показывает владельцу список файлов и предлагает перенести их в корень ветки `shared` с теми же именами (коммитом в ветку) и убрать из `main` отдельным PR. Делает это только после «да» владельца. Старые ссылки на файлы в `main` после удаления перестанут открываться: об этом тоже говорит.
5. Обновляет документы проекта, где упомянуты разборы или папка `shared/` (`README.md`, раздел «Проект» в `AGENTS.md`, `docs/`), PR по `docs/playbook/prepare-pr.md`.
6. Говорит владельцу ссылку на ветку и что сообщения бота о ней настраиваются в проекте бота.

## Клон playbook

- Скрипты берут правила из клона playbook рядом с репой проекта, по умолчанию `../playbook` (другой путь — `PLAYBOOK=<путь>`). В облачной среде клон подключённой репы лежит рядом сам, на компьютере владелец один раз клонирует playbook рядом с репами проектов.
- Обновить клон: `git -C ../playbook fetch origin main && git -C ../playbook checkout --detach origin/main`. `git pull` не годится: в облачной среде клон без ветки, и он падает. `make sync-rules` предупреждает, если клон отстал от `origin/main`.

## Справочник группы

Данные серверов и инфраструктуры (адреса, пользователи, папки проектов, как зайти) общие для нескольких проектов. Чтобы не копировать их в каждый проект и не давать в playbook (репа публичная), они лежат в одном месте — справочнике группы: отдельной приватной репе для людей. Агенты проектов её только читают, а правят — в её собственном проекте.

- В разделе «Проект» каждого проекта — строка «Справочник группы: <репа>, только читаем» (или «справочника нет»).
- В облаке репа справочника подключена к проекту (в Claude — в настройках проекта, раздел с репозиториями), на компьютере владелец один раз клонирует её рядом с репами проектов, как playbook (`../<репа>`). Её `AGENTS.md` агент тоже увидит, но раздел проекта берёт из репы своего проекта (`rules.md`).
- Агент читает справочник, прежде чем дать владельцу команду для сервера, и подставляет настоящие хост, пользователя и папку (`rules.md`, «Документы проекта»). В документах проекта (например, про деплой) вместо адреса сервера — ссылка на нужный раздел справочника.
- Секретов в справочнике нет: только где секрет лежит и кто даёт доступ.
- Справочник отстаёт, если проект поменял сервер, порты, деплой, контейнеры, места ключей или то, что он умеет и как им пользоваться. Поэтому агент проекта, открыв такой PR, сам даёт владельцу текст для проекта справочника: какие страницы и что поправить (`rules.md`, «Документы проекта»). Владелец пересылает его агенту справочника. Если в справочнике есть своя сверка с репами проектов, это не заменяет её, а закрывает то, что она не видит: факты, которых нет в её списке источников.
- Чтобы своя сверка справочника замечала новые возможности проекта, раздел «Что умеет и как пользоваться» в `README.md` проекта стоит в источниках страницы проекта в справочнике. Это правка в проекте справочника.

## Защита main

Правило «в `main` не пушить, PR мёрджит владелец» (`rules.md`, «Ветки, коммиты и PR») само по себе ничего не запрещает: без настройки GitHub в `main` можно запушить напрямую и смёрджить PR с красным CI. Поэтому у каждой репы проекта стоит рулсет на ветку по умолчанию (Settings → Rules → Rulesets): только через PR, обязательные проверки — все job CI репы, force-push и удаление запрещены, обхода нет ни для кого. Job, пропущенные по `if` на PR из одних документов, GitHub считает пройденными (раздел «CI не гоняем на документах»).

- Рулсеты есть в публичных репах на любом плане, а в приватных — только с платным планом (у личного аккаунта — GitHub Pro). На бесплатном плане API отвечает 403 «Upgrade to GitHub Pro or make this repository public»: такая репа остаётся без защиты, и правило о `main` держится только на тексте и проверках CI ([документация GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)).
- На личном аккаунте GitHub Actions в обход рулсета не добавить (422 «Actor GitHub Actions integration must be part of the ruleset source or owner organization»), это можно только в организации. Поэтому в репе проекта с рулсетом и обязательными проверками PR «<ключ>: обновить общие правила» сам не смёрджится: он открыт встроенным токеном, CI на нём не запускается, и проверки не придут. Такой PR владелец мёрджит руками.
- Если у группы есть справочник со своим workflow, который ставит рулсет всем репам по одному списку, защита ставится им: новая репа добавляется в список и в токен этого workflow. Руками рулсет ставят только там, где такого workflow нет.
- Агент проекта при сверке со списком «Что должно быть в проекте» читает рулсет через API и говорит владельцу, если защиты нет или она отличается. Сам рулсет агент не ставит: нужны права администратора репы.

## Облако и компьютер: что учесть агенту

Правила одни для любого агента, а среды разные: облако агента (Claude, Codex и другие) или компьютер владельца или участника. Перед работой агент проверяет в своей среде:

- **Инструкции.** Какие файлы агент читает сам (`AGENTS.md` или свой файл) и видны ли ему инструкции и память проекта. Инструкции и память облачного проекта не видны на компьютере, а облако не видит локальные сессии. Поэтому всё нужное агенту — в `AGENTS.md`, решения — в `docs/decisions.md`. Если загружены `AGENTS.md` нескольких реп, раздел проекта выбирается по `rules.md`, а подсказывают его вводные в инструкции проекта (раздел «Начать работу в проекте», шаг 4). Агенту без репы правила видны только из инструкции проекта, поэтому в ней блок из `procedures/no-repo-agent.md`.
- **Интернет и GitHub.** Облачная среда может быть без интернета или с урезанным доступом к GitHub. Без `github.com` не работают `git fetch` и push, ящик `/quack`, «кря» и проверка ветки и PR. Доступ включают в настройках среды (у участника — он сам в своей).
- **Ветки и PR.** Среда может предлагать свою ветку или открывать PR сама. Что делать — правило о ветках в `rules.md`.
- **Инструменты.** Docker, линтеры и `gh` могут быть не установлены, не запущены или ограничены. Что поставить заранее, добавляют в скрипт настройки среды (например, shellcheck для `make lint` этой репы: `apt update && apt install -y shellcheck`). Что агент делает сам — `procedures/prepare-pr.md`.
- **Автор и служебные строки.** Автор коммитов в облаке часто не тот, что нужен: у владельца — автор из раздела проекта, у участника — его собственный аккаунт. Проверить `git config`. Служебные строки агента в коммитах и PR лучше выключить в настройках самого агента, а где нельзя — убирать руками.
- **Серверы.** Агент сам на серверы не заходит и деплой руками не запускает (`rules.md`, «Документы проекта»). На компьютере он работает с ssh-ключами человека, в том числе админскими, поэтому `ssh`, `scp` и `rsync` лучше запретить агенту и технически, в его настройках. Для Claude Code это делает `.claude/settings.json` из `templates/.claude/` в репе проекта; для других агентов — в справочнике группы.
- **Трекер.** Если проект ведёт доску трекера (`procedures/tracker.md`), агенту нужны переменные окружения `TRACKER_URL` и `TRACKER_TOKEN` и доступ из среды к адресу трекера, в том числе запросы `POST`, `PATCH` и `DELETE`. Токен выпускает сам человек в вебе трекера, на странице «Агенты». В репу, чат и файлы проекта токен не кладём.
- **Перенос задачи** между облаком и компьютером — `procedures/new-thread.md`, раздел «Перейти между облаком и компьютером».

Ниже — что известно про конкретных агентов. Новый агент — новый подраздел с теми же пунктами.

### Claude

- Читает `CLAUDE.md`, поэтому в проекте `CLAUDE.md` — строка `@AGENTS.md`.
- Облачный тред проекта загружает `CLAUDE.md` каждой подключённой к проекту репы, но не `.claude/settings.json`, хуки и скиллы из реп. Лишние репы в проект не добавляй, тред подключит нужную сам. Репа справочника группы подключена к проекту постоянно (раздел «Справочник группы»). Репа playbook проекту нужна только на время перевода на правила и их обновления, а участнику — если тред не может прочитать раздел «Начать работу в проекте» с GitHub ([проекты](https://code.claude.com/docs/en/claude-projects.md)).
- В облачной среде Docker установлен, но не запущен; `gh pr` закрыт, PR — через GitHub-инструменты; автор коммитов по умолчанию — не человек, а сам агент; shellcheck нет ([облачная среда](https://code.claude.com/docs/en/cloud-environments.md)).
- Ветку `claude/…` среда предлагает, но запушить ветку по формату не мешает.
- На компьютере служебные строки выключает настройка `attribution` в `~/.claude/settings.json` ([настройки](https://code.claude.com/docs/en/settings-reference.md)).
- Токен трекера в облачном проекте: Настройки проекта → Cloud environment → Add cloud environment (у проекта без своей среды настроек нет). В Network access — Limited, в Allowed domains — `tracker.mixpool.dev`, галочку Allow package managers оставь. Там же переменные окружения `TRACKER_URL=https://tracker.mixpool.dev` и `TRACKER_TOKEN`. Адрес трекера — только по имени, не по IP: поле Allowed domains IP не принимает, а облачный прокси обрывает HTTPS на голый IP даже при Full. Треды, начатые после этого, берут среду сами ([облачная среда](https://code.claude.com/docs/en/cloud-environments#network-access)). На компьютере — переменные окружения в оболочке.
- В проекте Claude есть координатор: он отвечает в чате проекта, заводит треды и пересылает в них сообщения. Реп у него нет, только инструкции и память проекта (так говорит он сам, по документации не сверено), поэтому правила он знает только из блока `procedures/no-repo-agent.md` в инструкции проекта.
- Задачу, которой нужен компьютер владельца, можно вести тредом проекта на компьютере («Work locally»): так она остаётся в проекте ([облачные сессии](https://code.claude.com/docs/en/claude-code-on-the-web)).

### Codex

- Читает `AGENTS.md` сам; файлы по ссылке не подключает, лимит — 32 КиБ на все `AGENTS.md` вместе.
- В облаке интернет во время работы агента по умолчанию выключен, а у скрипта настройки он есть. Для git, ящика и «кря» доступ включают в настройках среды и разрешают домены GitHub ([доступ в интернет](https://learn.chatgpt.com/docs/cloud/internet-access)).
- Токен трекера: переменные окружения `TRACKER_URL` и `TRACKER_TOKEN` в настройках среды, не секреты — секреты видит только скрипт настройки, агенту они недоступны. Адрес — по имени (`TRACKER_URL=https://tracker.mixpool.dev`), в доступе в интернет для агента — `tracker.mixpool.dev` в списке доменов; если методы HTTP ограничены, нужны и `POST`, `PATCH`, иначе агент доску только читает ([облачная среда](https://learn.chatgpt.com/docs/environments/cloud-environment), [доступ в интернет](https://learn.chatgpt.com/docs/cloud/internet-access)).
- Как облачный Codex называет ветки и открывает PR, не проверено.

### Другие агенты

- Cursor и GitHub Copilot (coding agent) читают `AGENTS.md` сами.
- Gemini CLI по умолчанию читает `GEMINI.md`; чтобы читал `AGENTS.md`, нужна настройка `context.fileName` в `settings.json`.
- Обычный чат (ChatGPT и т.п.) не запускает команды и не пушит в репу: эта схема — для агентов, которые работают с кодом.
- Обычный чат и «Проекты» ChatGPT и похожих сервисов `AGENTS.md` не видят, только свои инструкции. Если в них обсуждают проект, туда вставляют блок из `procedures/no-repo-agent.md`.
