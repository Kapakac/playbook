# Playbook

Общие правила для всех проектов владельца, одинаковые для любого агента (Claude Code, Codex, Cursor, Copilot и других). Своих правил у проектов остаётся только то, что касается их самих.

## Что здесь

- `rules.md` — общие правила.
- `procedures/` — процедуры по шагам: подготовить PR, «кря» в Telegram, ящик `/quack`, новый тред, журнал сессий (необязательный).
- `templates/` — стартовые файлы проекта.
- `init.sh` — завести новый проект из шаблонов.
- `scripts/sync-rules.sh` — синхронизация и проверка правил в репе проекта.
- `AGENTS.md` — правила для агента, который правит саму playbook; `CLAUDE.md` подключает его для Claude.

## Как это устроено в репе проекта

- `AGENTS.md` — инструкции для всех агентов. Сверху название и пара строк о проекте, затем между метками `<!-- playbook:begin … -->` и `<!-- playbook:end -->` копия `rules.md` (в метке записан коммит playbook, из которого она взята), а под блоком раздел «Проект»: устройство, команды, параметры для общих правил и правила самого проекта.
- Необязательные процедуры включаются строкой в разделе «Проект». Сейчас такая одна — журнал сессий: «Журнал сессий: ведём, ветка `<имя>`». Строки нет — журнал не пишут.
- `CLAUDE.md` — одна строка `@AGENTS.md`. Новые версии Claude Code читают `AGENTS.md` и сами, но только когда `CLAUDE.md` нет; импорт работает во всех версиях и в облачных тредах, а дважды файл не загрузится ([документация](https://code.claude.com/docs/en/memory#agents-md)).
- `docs/playbook/` — копия `procedures/`.
- `make sync-rules` — обновить блок и `docs/playbook/` из клона playbook рядом с проектом (по умолчанию `../playbook`).
- `make check-rules` и workflow `.github/workflows/rules.yml` — CI падает, если блок или процедуры поправили руками, и предупреждает (не падает), если в playbook появились правила новее.

Почему копия, а не ссылка на playbook: Codex и часть других агентов не умеют подключать файл из `AGENTS.md` ссылкой, им нужен текст в самом файле.

## Новый проект

Проект заводит агент в собственном проекте новой репы, первым PR.

### Что делает владелец

1. Создаёт репу для проекта на GitHub с README (галочка «Add a README file»): в совсем пустой репе нет ветки `main`, и PR открыть некуда.
2. Подключает к проекту (в Claude — в настройках проекта, раздел с репозиториями) новую репу и репу playbook.
3. Пишет агенту в этом проекте:

   > Заведи проект по playbook: README playbook, раздел «Новый проект», часть «Что делает агент». Проект: <пара строк, что это и зачем>.

4. Проверяет PR агента и мёрджит его.
5. Пишет короткую инструкцию проекта (в Claude — в настройках проекта): агент предложит текст в PR.

### Что делает агент

1. Находит клон playbook рядом с репой проекта (`../playbook`). Если его нет, клонирует его туда сам или просит владельца подключить репу к проекту. Обновляет клон до свежего `main` (раздел «Клон playbook»).
2. Спрашивает у владельца то, чего нет в его сообщении и что нельзя придумать: ключ проекта, автор коммитов, нужен ли бот и ящик `/quack`, вести ли журнал.
3. Создаёт ветку по общим правилам и запускает `../playbook/init.sh . "<Название проекта>"`. Скрипт копирует шаблоны, не трогая существующие файлы, и сразу вклеивает общие правила (`make sync-rules`).
4. Заполняет раздел «Проект» в `AGENTS.md`, `docs/stack.md` и `docs/roadmap.md` по ответам и описанию владельца.
5. Открывает PR по `docs/playbook/prepare-pr.md`. В описании PR — готовый короткий текст инструкции проекта для владельца.

## Перевести существующий проект

Перевод делает агент в собственном проекте той репы, одним PR. Каждый проект переводится отдельно.

### Что делает владелец

1. Подключает репу playbook к этому проекту (в Claude — в настройках проекта, раздел с репозиториями), чтобы агент видел её рядом с репой проекта.
2. Пишет агенту в этом проекте:

   > Переведи проект на общие правила из playbook: README playbook, раздел «Перевести существующий проект», часть «Что делает агент».

3. Проверяет PR агента и мёрджит его.
4. После мёрджа заменяет инструкцию проекта (в Claude — в настройках проекта) коротким текстом, который агент предложил в PR.

### Что делает агент

1. Находит клон playbook рядом с репой проекта (`../playbook`). Если его нет, клонирует его туда сам или просит владельца подключить репу к проекту. Обновляет клон до свежего `main` (раздел «Клон playbook»).
2. Создаёт ветку по общим правилам и `AGENTS.md` из `templates/AGENTS.md`.
3. Переносит в раздел «Проект» всё своё, что относится только к этому проекту: из старого `CLAUDE.md` и из инструкции проекта (у кого `CLAUDE.md` нет — только из инструкции). Общие правила, которые уже есть в `rules.md`, не переносит. Заполняет параметры: ключ проекта, автор коммитов, бот, ящик `/quack`, адресат «кря», хелпер тестов, внешние сервисы. Если проект ведёт журнал, добавляет строку «Журнал сессий: ведём, ветка …» с нынешней веткой журнала.
4. Заменяет `CLAUDE.md` одной строкой `@AGENTS.md`.
5. Добавляет в `Makefile` цели `sync-rules` и `check-rules` из `templates/Makefile`, в `.github/workflows/` — `templates/.github/workflows/rules.yml`, а если нет шаблона PR — `templates/.github/pull_request_template.md`.
6. Запускает `make sync-rules`, затем `make check-rules`.
7. Если есть скиллы `.claude/skills/prepare-pr` и `send-to-group`, сводит их к ссылке на `docs/playbook/`.
8. Если в `docs/duck-log.md` нет строки «Просмотрено до №N», добавляет её с самым большим уже разобранным номером. Если у проекта ящик есть, а `docs/duck-log.md` нет, берёт его из `templates/docs/`.
9. Открывает PR по `docs/playbook/prepare-pr.md`. В описании PR — что из старых правил куда переехало, какие правила проекта расходились с общими и чем их заменили, и готовый короткий текст новой инструкции проекта для владельца.

## Начать работу в проекте

Для участника, которого владелец позвал в проект. Своих правил у участника нет: работа идёт по `rules.md` и разделу «Проект» в `AGENTS.md` репы проекта.

1. Пришли владельцу свой ник на GitHub и скажи, в какой проект. Доступ к репе проекта даёт он; эта репа публичная, к ней доступ не нужен.
2. Склонируй рядом репу проекта и эту репу в папку `playbook`, чтобы получилось `<папка>/<репа проекта>` и `<папка>/playbook`. Правила и процедуры уже лежат в репе проекта (`AGENTS.md` и `docs/playbook/`), а клон рядом нужен `make sync-rules` и `make check-rules`.
3. Прочитай `README.md` проекта и раздел «Проект» в его `AGENTS.md`: ключ проекта, команды, правила проекта.
4. Открой своего агента в папке репы проекта. `AGENTS.md` он прочитает сам, Claude — через `CLAUDE.md`. Что учесть для твоего агента — раздел [«Облако и компьютер: что учесть агенту»](#облако-и-компьютер-что-учесть-агенту).
5. Работай по `rules.md`: ветка `<ключ проекта>-<задача>-<тема>-<суффикс>`, заголовок PR с ключа, коммиты со своего аккаунта, перед PR — `docs/playbook/prepare-pr.md`. В `main` не пушь, PR мёрджит владелец. Где правила требуют согласия владельца, это согласие самого владельца, а не твоё: спроси его в чате.
6. Если у проекта есть ящик `/quack`, заметки для агента пиши в Telegram-группе командой `/quack <метка> …` (метка — в разделе «Проект»): бот положит их в ящик проекта. Агент разбирает их по `docs/playbook/quack-inbox.md` и ничего по ним не делает без «да» владельца.

## Поменять общие правила

1. Правка — PR в playbook (`rules.md`, `procedures/`, шаблоны или скрипты). Перед PR — `make lint` и `make test`.
2. После мёрджа CI проектов начнёт предупреждать, что в playbook есть правила новее. Владелец пишет агенту в каждом проекте: «Обнови общие правила из playbook». Агент обновляет клон playbook (раздел «Клон playbook»), запускает `make sync-rules`, сверяет `.github/pull_request_template.md` проекта с `templates/.github/pull_request_template.md` и добавляет в него новые строки из playbook (свои строки проекта не трогает), затем открывает отдельный PR. Что добавил в шаблон — в описании PR.

При правке помни:

- Репа публичная: никаких секретов, имён, ников и других личных данных, названий и подробностей конкретных проектов. Всё конкретное — в разделе «Проект» самих проектов.
- `rules.md` вклеивается в `AGENTS.md` каждого проекта, а Codex читает не больше 32 КиБ инструкций на все `AGENTS.md` вместе. Поэтому `rules.md` держим коротким, подробности — в процедурах.
- Правило, которое касается одного проекта, сюда не кладём: ему место в разделе «Проект» того проекта.
- Если после правки проектам нужно что-то сделать руками (новый параметр в разделе проекта, новый файл), напиши это в описании PR.
- Своих `docs/` у playbook нет: агент открывает эту репу только для правки правил. `AGENTS.md` отсылает к `rules.md` и даёт параметры вместо раздела «Проект»: так агент на компьютере владельца, где нет инструкции проекта, знает правила и то, что репа публичная. `CLAUDE.md` подключает `AGENTS.md` и `rules.md` для Claude.

## Клон playbook

- Скрипты берут правила из клона playbook рядом с репой проекта, по умолчанию `../playbook` (другой путь — `PLAYBOOK=<путь>`). В облачной среде клон подключённой репы лежит рядом сам, на компьютере владелец один раз клонирует playbook рядом с репами проектов.
- Обновить клон: `git -C ../playbook fetch origin main && git -C ../playbook checkout --detach origin/main`. `git pull` не годится: в облачной среде клон без ветки, и он падает. `make sync-rules` предупреждает, если клон отстал от `origin/main`.

## Облако и компьютер: что учесть агенту

Правила одни для любого агента, а среды разные: облако агента (Claude, Codex и другие) или компьютер владельца. Перед работой агент проверяет в своей среде:

- **Инструкции.** Какие файлы агент читает сам (`AGENTS.md` или свой файл) и видны ли ему инструкции и память проекта. Инструкции и память облачного проекта не видны на компьютере, а облако не видит локальные сессии. Поэтому всё нужное агенту — в `AGENTS.md`, решения — в `docs/decisions.md`. Если загружены `AGENTS.md` нескольких реп, раздел проекта выбирается по `rules.md`.
- **Интернет и GitHub.** Облачная среда может быть без интернета или с урезанным доступом к GitHub. Без `github.com` не работают `git fetch` и push, ящик `/quack`, «кря» и проверка ветки и PR. Доступ включает владелец в настройках среды.
- **Ветки и PR.** Среда может предлагать свою ветку или открывать PR сама. Что делать — правило о ветках в `rules.md`.
- **Инструменты.** Docker, линтеры и `gh` могут быть не установлены, не запущены или ограничены. Что поставить заранее, владелец добавляет в скрипт настройки среды (например, shellcheck для `make lint` этой репы: `apt update && apt install -y shellcheck`). Что агент делает сам — `procedures/prepare-pr.md`.
- **Автор и служебные строки.** Автор коммитов в облаке часто не владелец: проверить `git config`. Служебные строки агента в коммитах и PR лучше выключить в настройках самого агента, а где нельзя — убирать руками.
- **Перенос задачи** между облаком и компьютером — `procedures/new-thread.md`, раздел «Перейти между облаком и компьютером».

Ниже — что известно про конкретных агентов. Новый агент — новый подраздел с теми же пунктами.

### Claude

- Читает `CLAUDE.md`, поэтому в проекте `CLAUDE.md` — строка `@AGENTS.md`.
- Облачный тред проекта загружает `CLAUDE.md` каждой подключённой к проекту репы, но не `.claude/settings.json`, хуки и скиллы из реп. Лишние репы в проект не добавляй, тред подключит нужную сам. Репа playbook проекту нужна только на время перевода на правила и их обновления ([проекты](https://code.claude.com/docs/en/claude-projects.md)).
- В облачной среде Docker установлен, но не запущен; `gh pr` закрыт, PR — через GitHub-инструменты; автор коммитов по умолчанию не владелец; shellcheck нет ([облачная среда](https://code.claude.com/docs/en/cloud-environments.md)).
- Ветку `claude/…` среда предлагает, но запушить ветку по формату не мешает.
- На компьютере служебные строки выключает настройка `attribution` в `~/.claude/settings.json` ([настройки](https://code.claude.com/docs/en/settings-reference.md)).
- Задачу, которой нужен компьютер владельца, можно вести тредом проекта на компьютере («Work locally»): так она остаётся в проекте ([облачные сессии](https://code.claude.com/docs/en/claude-code-on-the-web)).

### Codex

- Читает `AGENTS.md` сам; файлы по ссылке не подключает, лимит — 32 КиБ на все `AGENTS.md` вместе.
- В облаке интернет во время работы агента по умолчанию выключен, а у скрипта настройки он есть. Для git, ящика и «кря» владелец включает доступ в настройках среды и разрешает домены GitHub ([доступ в интернет](https://learn.chatgpt.com/docs/cloud/internet-access)).
- Как облачный Codex называет ветки и открывает PR, не проверено.

### Другие агенты

- Cursor и GitHub Copilot (coding agent) читают `AGENTS.md` сами.
- Gemini CLI по умолчанию читает `GEMINI.md`; чтобы читал `AGENTS.md`, нужна настройка `context.fileName` в `settings.json`.
- Обычный чат (ChatGPT и т.п.) не запускает команды и не пушит в репу: эта схема — для агентов, которые работают с кодом.
